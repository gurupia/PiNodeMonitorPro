# 웹 기반 원격 제어 기술의 핵심 원리 (Core Principles of Web-Based Remote Control)

본 문서는 Pi Node Monitor의 원격 제어 기능을 구현하기 위해 사용된 핵심 기술들(화면 캡처, 스트리밍, 입력 제어)의 작동 원리와 배경 지식을 정리한 기술 자료입니다.
원격 제어 및 스트리밍 시스템 개발에 입문하는 개발자를 위한 참고 자료로 활용됩니다.

---

## 1. 화면 캡처 기술 (Screen Capture Technologies)

화면을 "보는" 기술입니다. 윈도우 환경에서는 크게 두 가지 방식이 사용됩니다.

### 1.1 GDI+ (Graphics Device Interface)
- **방식**: CPU가 주도하여 화면의 픽셀 데이터를 메모리로 복사하는 전통적인 방식입니다.
- **원리**: `Graphics.CopyFromScreen()` 함수를 호출하면, 운영체제는 현재 화면의 비트맵을 시스템 메모리(RAM)에 픽셀 단위로 씁니다.
- **특징**:
  - **장점**: 구현이 매우 쉽고, Windows XP부터 최신 버전까지 호환성이 뛰어납니다.
  - **단점**: CPU 점유율이 높고 속도가 느립니다 (보통 10~20 FPS 한계). 화면 해상도가 높을수록 급격히 느려집니다.

### 1.2 DXGI (DirectX Graphics Infrastructure) - Desktop Duplication API
- **방식**: GPU(그래픽 카드) 메모리에 있는 화면 버퍼를 직접 접근하여 가져오는 고성능 방식입니다.
- **원리**: CPU가 픽셀을 일일이 복사하는 대신, 비디오 카드(VRAM) 내에서 "이 이미지를 저쪽으로 옮겨라"라고 명령만 내립니다(Zero-copy에 가까움).
- **특징**:
  - **장점**: CPU 부하가 거의 없이 60 FPS 이상의 고해상도 캡처가 가능합니다. 게임 방송이나 고성능 원격 제어(TeamViewer 등)에서 사용합니다.
  - **단점**: 구현이 복잡하며(C++/DirectX 지식 필요), Windows 8 이상에서만 동작합니다. 특정 전체화면 게임이나 보안 프로그램에 의해 차단될 수 있습니다.

## 2. 영상 스트리밍 프로토콜 (MJPEG via HTTP)

캡처한 화면을 클라이언트로 "보내는" 기술입니다. 우리는 복잡한 WebRTC 대신 단순하고 강력한 MJPEG를 사용했습니다.

### 2.1 MJPEG (Motion JPEG)
- **정의**: 비디오 코덱(H.264 등)을 쓰지 않고, **JPEG 사진을 아주 빠르게 연속으로 보여주는 방식**입니다.
- **구조**:
  ```http
  HTTP/1.1 200 OK
  Content-Type: multipart/x-mixed-replace; boundary=--frame

  --frame
  Content-Type: image/jpeg
  (JPEG 바이너리 데이터 1)
  
  --frame
  Content-Type: image/jpeg
  (JPEG 바이너리 데이터 2)
  ...
  ```
- **원리**: 브라우저는 `multipart/x-mixed-replace` 헤더를 보면 "아, 파일 하나로 끝나는 게 아니라 계속 내용이 바뀌겠구나"라고 인지하고, 구분자(`boundary`)가 나올 때마다 이미지를 새로고침(Refresh)합니다.
- **장점**: `<img src="...">` 태그 하나만 있으면 PC, 모바일, 냉장고(?) 등 웹 브라우저가 있는 모든 기기에서 별도 플러그인 없이 재생됩니다.
- **단점**: 압축 효율이 낮아 대역폭을 많이 씁니다(H.264 대비 5~10배). 오디오 전송이 불가능합니다.

## 3. 원격 입력 제어 (Remote Input Simulation)

클라이언트의 마우스/키보드 동작을 서버 PC에 "재현하는" 기술입니다.

### 3.1 Win32 API (`user32.dll`)
운영체제(Windows)는 하드웨어(마우스/키보드)에서 신호가 오면 **메시지 큐(Message Queue)**에 이벤트를 쌓습니다. 우리는 소프트웨어적으로 이 큐에 가짜 이벤트를 집어넣습니다.

### 3.2 `SetCursorPos` vs `mouse_event`
- **`SetCursorPos(x, y)`**:
  - 마우스 커서를 해당 좌표로 **순간 이동(Teleport)**시킵니다.
  - 단순 클릭에는 문제가 없으나, 드래그 동작(이동 경로가 중요한 동작)에는 적합하지 않습니다. OS는 이를 "이동"으로 치지 않습니다.
- **`mouse_event` (또는 `SendInput`)**:
  - 마우스 하드웨어 신호를 흉내 냅니다.
  - **절대 좌표계 (0 ~ 65535)**: 픽셀 좌표가 아닌, 화면 전체를 0에서 65535로 나눈 정규화된 좌표를 사용합니다.
  - `MOUSEEVENTF_ABSOLUTE | MOUSEEVENTF_MOVE` 플래그를 사용하면, OS는 "사용자가 물리적으로 마우스를 이 위치까지 밀었다"라고 인식하여 드래그 이벤트를 정상적으로 발생시킵니다.

## 4. 좌표계 변환 (Coordinate Mapping)

클라이언트(웹 브라우저)와 서버(PC 화면)의 해상도가 다르기 때문에 "비율 변환"이 필수적입니다.

### 4.1 변환 공식
```text
서버X = (클라이언트_클릭X / 클라이언트_영상너비) * 서버_화면너비
서버Y = (클라이언트_클릭Y / 클라이언트_영상높이) * 서버_화면높이
```

### 4.2 고려 사항 (Pitfalls)
- **Letterboxing**: 영상이 화면 비율을 유지하느라 생기는 검은 여백(Black bar)을 고려해야 합니다.
- **DPI Scaling**: 윈도우의 "텍스트 확대/축소(125%, 150%)" 설정에 따라 물리 픽셀과 논리 픽셀이 달라질 수 있어, 이를 보정해야 정확한 위치를 클릭할 수 있습니다.

## 5. 기술적 선택과 대안 (Technology Choices & Alternatives)

### 5.1 왜 구글 원격 데스크톱(WebRTC) 방식을 쓰지 않았는가?
구글 원격 데스크톱이나 팀뷰어는 **WebRTC** 또는 독자적인 UDP 기반 프로토콜을 사용합니다. 이는 MJPEG보다 기술적으로 진보된 방식이지만, 본 프로젝트("가벼운 단일 실행 파일")에는 다음과 같은 이유로 채택되지 않았습니다.

| 기술 | **WebRTC (구글 방식)** | **MJPEG (현재 방식)** |
| :--- | :--- | :--- |
| **전송 프로토콜** | **UDP**: 빠르고 지연이 거의 없음 (Low Latency) | **TCP/HTTP**: 순서 보장으로 인해 약간의 지연 발생 |
| **인프라 요구** | **Signaling/STUN/TURN 서버 필수**: P2P 연결을 중계할 외부 서버가 없으면 작동 불가 | **서버 불필요**: 오직 로컬 PC 내장 웹서버만으로 독립 작동 |
| **구현 복잡도** | **최상**: C++ 네이티브 라이브러리 연동 및 방화벽 처리 복잡 | **하**: HTTP 표준만 준수하면 구현 용이 |
| **의존성** | 수십 MB 이상의 비디오 코덱 라이브러리 필요 | 외부 라이브러리 없이 .NET 기본 기능만으로 구현 |

### 5.2 결론
Pi Node Monitor는 **"설치가 필요 없고, 외부 서버 의존성이 없는 독립적인 도구"**를 지향하므로, 호환성이 가장 높고 가벼운 **MJPEG + DXGI(가속) + Win32(입력)** 방식을 채택했습니다. 이는 범용성과 성능 사이의 최적의 타협점입니다.
