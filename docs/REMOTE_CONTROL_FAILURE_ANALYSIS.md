# 원격 제어 드래그 앤 드롭 구현 실패 사례 분석 (Failure Analysis of Web-Based Remote Control)

본 문서는 Pi Node Monitor의 웹 기반 원격 제어 기능 개발 과정에서 시도되었으나, **PC 브라우저 환경에서 드래그 앤 드롭(Drag & Drop)을 완벽하게 구현하는 데 실패한 기술적 접근 방식들**을 기록합니다.
이 기록은 향후 동일한 기능 구현 시 시행착오를 줄이기 위한 '실패 노트'로 활용됩니다.

---

## ⛔ 실패한 접근 방식 (Failed Approaches)

### 1. `<img>` 태그 직접 이벤트 바인딩
- **시도**: 스트리밍되는 `<img>` 태그에 `onmousedown`, `onmousemove` 이벤트를 직접 연결.
- **실패 원인**:
  - **Ghost Image**: PC 브라우저는 이미지를 드래그할 때, 이미지 파일 자체를 바탕화면으로 끌어다 놓으려는 **네이티브 동작(Ghost Image Drag)**이 우선 발동됨.
  - **이벤트 차단**: 이 네이티브 동작이 발동하는 순간, 자바스크립트의 `mousemove` 이벤트가 브라우저에 의해 차단되거나 끊김.

### 2. CSS 및 속성을 통한 드래그 방지
- **시도**: `draggable="false"`, `user-select: none`, `-webkit-user-drag: none` 등의 속성 추가.
- **실패 원인**:
  - **브라우저 파편화**: 크롬, 엣지 등 브라우저마다 해당 속성을 처리하는 방식이 미묘하게 다름.
  - **완전 차단 불가**: 특정 상황(이미지 로딩 중, 텍스트 선택과 겹칠 때 등)에서 여전히 브라우저의 기본 드래그 동작이 간헐적으로 튀어나와 원격 제어를 방해함.

### 3. 자바스크립트 Window Global Listener
- **시도**: `mousemove` 이벤트를 `img`가 아닌 `window` 전역 객체에 걸어, 마우스가 이미지 밖으로 나가도 추적하도록 함.
- **실패 원인**:
  - **좌표 보정 한계**: 마우스가 브라우저 창 밖으로 나갔을 때 `clientX/Y` 값이 멈추거나 엉뚱한 값을 반환하여, 창을 화면 구석으로 끝까지 미는 동작이 불가능했음.
  - **포커스 유실**: MJPEG 이미지가 새로고침(`multipart/x-mixed-replace`)되는 순간, 미세하게 DOM 포커스가 튀거나 렌더링 엔진이 바쁘게 돌아가면서 마우스 이벤트 틱(Tick)이 씹히는 현상 발생.

### 4. 투명 오버레이 실드 (Overlay Shield) 패턴
- **시도**: 영상 위에 투명한 `div`(`z-index` 높음)를 씌워, 영상 교체와 상관없이 입력을 전담 처리.
- **실패 원인**:
  - **이론상 최선이었으나 실패**: 구조적으로는 가장 안정적이어야 했으나, 실제 테스트 결과 여전히 PC에서 드래그가 매끄럽지 않음.
  - **원인 추정**: HTTP 요청(`fetch`)의 **비동기 지연(Latency)** 문제로 추정됨. 마우스를 빠르게 흔들면 `Move` 요청이 수십 개 쌓이는데, 서버가 이를 순서대로 처리하지 못하거나, 네트워크 큐에서 `Down` -> `Move` -> `Up` 순서가 뒤섞여 도착할 가능성이 있음. (UDP가 아닌 HTTP의 한계)

### 5. Win32 `SetCursorPos` (단순 좌표 이동)
- **시도**: 서버에서 `SetCursorPos(x, y)` API 사용.
- **실패 원인**:
  - **텔레포트 판정**: OS는 이를 "마우스 이동"이 아닌 "좌표 텔레포트"로 인식함.
  - **드래그 불가**: 마우스 버튼을 누른 채로 좌표가 순간 이동하면, 윈도우 창 관리자는 이를 드래그로 인식하지 않고 "클릭 후 다른 곳에서 버튼 뗌"으로 인식함.

### 6. Win32 `mouse_event` (하드웨어 시뮬레이션)
- **시도**: `mouse_event(ABSOLUTE | MOVE, ...)`를 사용하여 하드웨어 신호 모사.
- **실패 원인**:
  - **여전한 불통**: 이론적으로는 완벽한 하드웨어 에뮬레이션이지만, 실제 사용자 환경에서는 여전히 드래그가 되지 않음.
  - **원인 추정**: 앞서 언급한 **HTTP 통신의 순서 보장 문제**와 결합되어, `Down` 이벤트가 처리되기도 전에 `Move` 이벤트가 먼저 도착하거나 유실되어, OS가 드래그 시퀀스(`Down`...`Move`...`Move`)를 완성하지 못하는 것으로 보임.

---

## 📝 결론 및 교훈 (Conclusion)

- **HTTP/TCP의 한계**: 실시간 마우스 드래그와 같이 **수 밀리초(ms) 단위의 순서 보장**이 생명인 기능은, HTTP 요청(`fetch`) 방식으로는 한계가 명확함. (Websocket이나 UDP가 필수적임)
- **웹 브라우저의 한계**: 네이티브 앱(RustDesk, TeamViewer)처럼 OS 레벨 마우스 훅을 사용할 수 없는 웹 환경에서는, 브라우저의 간섭을 100% 차단하기가 매우 어려움.
- **현재 상태**: 모바일(터치) 환경에서는 "클릭 앤 무브" 방식이 그나마 작동하지만, **PC(마우스) 환경에서의 정교한 드래그 앤 드롭은 현재 아키텍처(HTTP Polling/Streaming)로는 구현 불가능 판정.**

> **상태**: 구현 실패 (Deprecated)
> **권장 대안**: 웹 기반 제어는 '클릭' 위주의 단순 제어에 집중하고, 정교한 작업은 네이티브 원격 제어 툴 권장.
